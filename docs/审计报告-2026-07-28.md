## 一、执行摘要

### 整体评价

项目工程基线**显著高于一般中小型 SaaS**：JWT 密钥强度校验、RefreshToken Lua 原子消费、BCrypt cost=12、SSRF 防护、SQL 全参数化、CORS 严格白名单、Electron 沙箱+contextIsolation+safeStorage、DOMPurify 富文本清理、红包乐观锁+行锁+原子 SQL 三重并发防护、余额原子扣减、统一 `Result<T>` 返回、GlobalExceptionHandler 不暴露堆栈。**未发现 SQL 注入、IDOR、RCE 等可直接利用的致命漏洞**。

但存在 **7 项严重问题**集中在：**资金类并发缺陷、凭证明文泄露、Actuator 信息暴露、Electron 任意文件执行**，必须立即处置。

## 二、P0 严重问题（立即修复，24 小时内）

### 🔴 P0-1 红包领取重试在 @Transactional 内失效，并发抢包必失败
- **位置**: `linkx-server/src/main/java/com/linkx/server/service/impl/RedPacketServiceImpl.java:93-193`
- **根因**: InnoDB REPEATABLE_READ 下同一事务内 `selectOneById` 是快照读，乐观锁冲突后 `continue` 重试仍读旧 version，三次重试必然全部失败
- **影响**: 高并发抢红包场景下，凡发生乐观锁冲突的领取全部失败，用户领不到红包
- **修复**: 重试循环移出事务，或每次重试用 `Propagation.REQUIRES_NEW`（需通过独立 Bean 或 `AopContext.currentProxy()` 调用避免自调用失效），或改 `SELECT ... FOR UPDATE` 悲观锁

### 🔴 P0-2 红包发送接口无幂等性，重复提交导致重复扣款
- **位置**: `linkx-server/src/main/java/com/linkx/server/controller/RedPacketController.java:30-36`、`SendRedPacketDTO`（无 clientMsgId 字段）、`RedPacketServiceImpl.java:42-89`
- **根因**: `POST /red-packet` 无幂等键，对比 `SendMessageDTO` 已有 `clientMsgId`
- **影响**: 网络重试/用户双击触发重复请求，每次扣冻结余额并插入新红包，直接资金损失
- **修复**: DTO 增加 `@NotBlank clientMsgId`；service 入口 Redis `SETNX linkx:redpacket:idem:{userId}:{clientMsgId}` 做幂等锁；DB 加 `(sender_id, client_msg_id)` 唯一索引兜底

### 🔴 P0-3 client_msg_id 全局唯一约束跨用户碰撞导致 500 与消息丢失
- **位置**: `linkx-server/init.sql:229` `UNIQUE KEY uk_client_msg_id (client_msg_id)`
- **根因**: 应用层去重键是用户级（`linkx:msg:dedup:{userId}:{clientMsgId}`），DB 唯一约束却是全局
- **影响**: 两用户碰巧相同 clientMsgId 时第二位用户 `insert` 抛 `DuplicateKeyException` 上抛 500，消息丢失且 Redis 去重键已写入阻塞 10 分钟重试
- **修复**: 改为 `UNIQUE KEY uk_sender_client_msg (sender_id, client_msg_id)`

### 🔴 P0-4 Token 刷新分布式锁不安全（锁值固定 + 无防误删）
- **位置**: `linkx-server/src/main/java/com/linkx/server/service/impl/TokenServiceImpl.java:110-145`
- **根因**: `setIfAbsent(lockKey, "1", 5s)` 锁值固定，`finally` 中 `delete(lockKey)` 不校验值；线程 A 持锁超时后线程 B 获锁，A 释放时误删 B 的锁
- **影响**: 并发刷新产生多对有效 Token，破坏 Token 唯一性，可被重放
- **修复**: 锁值用 `UUID.randomUUID()`，释放用 Lua 脚本 `if get==value then del`，TTL 适当延长或加 watchdog

### 🔴 P0-5 .env.local 含真实邮箱授权码与可用凭证
- **位置**: `linkx-server/.env.local:94,96,36,74-76,16`
- **凭证**: QQ 邮箱 `liming743258831@qq.com` 授权码 `ogunqofycyvbbejf`、Redis `redis123`、MinIO `minioadmin/minioadmin123`、JWT 弱密钥
- **影响**: 授权码可登录邮箱发信/重置任意账号密码；虽 .gitignore 已忽略，但文件存在于磁盘，误提交/备份泄露即不可逆
- **修复**: 立即吊销 QQ 邮箱授权码、重置 Redis/MinIO 凭证为强随机值；`git log --all --full-history` 确认未入历史；改用系统环境变量或 Docker secrets

### 🔴 P0-6 Actuator /actuator/info 暴露 Environment 全量属性
- **位置**: `linkx-server/src/main/resources/application.yml:176-178` `info.env.enabled: true`、`linkx-server/src/main/java/com/linkx/server/config/WebMvcConfig.java:54` 放行 `/actuator/info`
- **影响**: 无需认证即可访问 `/api/actuator/info` 获取 DB_URL、MinIO 地址、邮箱账号、CORS 配置等内部架构信息
- **修复**: 删除 `info.env.enabled: true`；从放行列表移除 `/actuator/info`；生产 `MANAGEMENT_ENDPOINTS=health`

### 🔴 P0-7 Electron 下载更新接口可执行任意来源可执行文件（RCE）
- **位置**: `linkx-client/electron/main.ts:629-693` `app:download-and-install-update`
- **根因**: 仅校验 `^https?://`，不校验域名白名单、不做签名校验，下载后直接 `shell.openPath(targetPath)`
- **影响**: 渲染进程被 XSS 攻破后可下载任意 exe 自动执行，等价 RCE
- **修复**: 硬编码更新源域名白名单；校验 Authenticode 签名；改用 `electron-updater` 官方组件；`shell.openPath` 前提示用户确认

| CORS | 严格白名单，未配置时拒绝所有跨域，未使用通配 |
| 安全头 | X-Content-Type-Options、X-Frame-Options、Referrer-Policy、CSP、HSTS（HTTPS） |
| 红包并发 | 乐观锁 + DB 唯一约束（除 P0-1 重试缺陷外） |
| 余额 | 原子 SQL `WHERE balance >= amount` + affectedRows 校验 |
| 文件上传 | UUID 命名 + sanitizeFilename 防穿越 + 扩展名白名单（除 magic bytes 缺失外） |

| 富文本 | NoteEditor marked + DOMPurify（ADD_TAGS audio） |
| WebSocket | token 走 Sec-WebSocket-Protocol 子协议，不进 URL |
| 持久化 | persistSanitize 清理预签名 URL，messagesBySession 用 sessionStorage |
